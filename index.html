03问题

模型越来越快之后，卡住的变成了人

3–5

文章里的经验：一个人同时能跟住的活跃会话，大概就 3 到 5 个。

再多开几个，Agent 做得再快，也只能排队等人看、等人点头。

DeepSeek Super-agent 设计文与开源原型会话越开越多会怎样
文章的出发点：做单个任务时，瓶颈是模型能力；同时做很多任务时，瓶颈变成了人的注意力和精力。3–5 是作者的经验值，不是实验数字。 可以点开小模拟：会话越开越多时，排队等你的会越积越多。

原文的四个特征：Continuous、Productive、Proactive、Persistent。文章强调这些不是靠一个更强的 ReAct 循环得到的，而是靠系统架构；也说明他们没有提新理论，是把计算机系统里的老办法搬过来。
06怎么拆

拆成两层：前台只负责接话和派活，干活的在后面

Router

一个任务一个干净会话
Worker B
完整工具，最强模型
Worker C
不直接找你，向前台汇报

前台连命令行都可以不给；通常用轻一点的模型就够。

DeepSeek Super-agent 设计文与开源原型看一条消息怎么走
Router：所有和人的交互、全局协调、记忆都在这层，但它不执行任务，可以完全没有 Bash。原文说轻量模型「通常」就能兼顾速度和质量。 Worker：每个任务一个隔离会话，带全套工具，一般需要最强的模型。 和常见 Agent Team 的区别：Router 只派发，不负责把任务拆细。 忙的时候到达的消息会攒成一批，下一轮一起处理。他们压测过：需要决策的消息从每分钟约 1 条涨到约 40 条，每条决策摊下来的推理时间反而从 6.4 秒降到 1.6 秒，所以现在这个规模不急着拆 Router。

DeepSeek Super-agent 设计文与开源原型完整结构图
第一道是确定性规则：按来源、群、用户、bot 白名单准入；每个来源还可以设成「只响应明确找我的」「算作候选」或「忽略」。 过了第一道的候选才进第二道，用模型做语义判断，策略写成 prompt，可以随时加改。 原型里的做法也是这样：名单里的人 @ 它或私聊算明确请求；其它按表格判断；已经在处理的话题里的消息算跟进。

DeepSeek Super-agent 设计文与开源原型对比：经前台 vs 直送
原文叫 Thread 订阅 / pass-through。Router 为一个话题的第一条消息派了 Worker 后，这个 Worker 就订阅这个话题；之后同话题的消息由代码直接送过去，Router 仍然看得见，只是不用再判断和转发。 订阅是多对多的：几个 Worker 订阅同一个话题，就能自己发现彼此冲突，Worker 之间不点对点通信。 原型里：飞书话题回复挂到根消息；GitHub 按 issue/PR 号。主聊天里不带话题的新消息，前台只有在它明确指向某个工单时才归过去，「话题相似不够」。

12实验

他们做了个实验：同一批消息，四种设计各跑 5 次

设计完成时间（分钟）
中位 / 慢的那 5%		每次读缓存的 token
完整 Super-agent12.4 / 15.723.2M
去掉话题直送12.6 / 15.531.8M
单会话 + 子 agent，中性 prompt20.4 / 29.56.1M

每次约 300 条群聊和 CI 消息，其中约 20 条是真要干的活；写代码用耗时工具模拟。文章自己说是合成负载，数字当方向看。

只测调度和协调，不测代码写得好不好。p95 就是「慢的那 5% 要多久」，代表长尾。 接下来两页各讲一个看点。
13实验

话题直送没让任务变快，但省下了一截 token

有直送23.2M
没有直送31.8M

完成时间几乎一样（12.4 vs 12.6 分钟）。去掉直送后前台要多做约 30% 的决策，读缓存的 token 多了约 37%。

DeepSeek Super-agent 设计文与开源原型动画对比
原文原话大意：直送并不会让任务完成得更快或更好，它省的是前台反复读长上下文的开销。 注意这里的 token 是所有会话「读缓存」的 token，不是总花费。
14实验

靠 prompt 让模型“记得委派”，不太靠得住

0 / 5

中性 prompt：5 次里一次都没叫子 agent，全自己干。

4 / 5

写明「优先委派」：还是有 1 次模型觉得活小，自己上了，结果拖出长尾。

DeepSeek Super-agent 设计文与开源原型
这就是表里 p95 一直在 29 分钟左右的原因。 所以他们的思路是：该不该委派、该不该出声，尽量用系统结构定下来，而不是寄希望于 prompt 里一句话。 另一面：Super-agent 读缓存的 token 是单会话的好几倍，是在用 token 换更短、更稳的完成时间。
15原型

开源原型里，能看到更落地的做法

一事一工单

每个工单一个 Worker 会话和独立工作目录；面板上只显示需要人处理的事

权限不听聊天的

白名单、规则由宿主程序强制；消息和文档只是参考，改不了权限

主动先只记录

想让它主动干活，要团队先写规则，并从「只记下会做什么」开始

它的说话原则也很朴素：尽量少占人的注意力；只在有人必须行动或能用上结果时开口；一次只问一个具体问题。

DeepSeek Super-agent 设计文与开源原型
原型 dsh-superagent-prototype，MIT，面向单个 GitHub 仓库的主动 coding agent，可选接飞书。概念有 Ticket（工单）、Executor、Mandate、SQLite 账本。 工单结束后仍保留订阅，人再说话就按原来的授权复活；为了看上下文而订阅，不会因此获得权限。
16边界

也要看清楚：这还是一份研究代码

不是正式产品

文章和原型都这么说；原型和内部版本、文章也不完全一致

权限给得很宽

两个预设都以完全访问权限、用你的系统用户运行，文档建议用专门账号隔离

安全是公开的难题

一直在线、主动、接群聊输入，提示注入的面变大了

DeepSeek Super-agent 设计文与开源原型
原文自己把安全列为开放问题：云端循环被注入，可能波及所有连着的设备；他们提到 agent 需要「能用凭证但看不到凭证」。 第三方评论也提到：main Session 能改团队的 skills 和策略，靠的是 prompt 里要求它先等人确认。
