DeepSeek Super-agent 设计文与开源原型
乍一看，一个中心派活给几个执行者，很像常见的 Agent Team。但关注点不同： Agent Team 通常把一个复杂任务拆成紧耦合的步骤，队长要深入理解任务、规划子任务、频繁协调成员，推理负担很重。 Super-agent 的前台只派发任务、在高层跟踪任务之间的关系，不拆解单个任务。 所以作者的经验是：前台的活往往比想象中简单，轻一点的模型通常就能兼顾速度和质量。注意原文是「通常」，不是规定。 反过来，Agent Team 也可以当两层架构用，只要用 prompt 限制主会话不自己干活、只对外交互和派活。

DeepSeek 对 Router 的单独压测 · 真实模型 + mock Worker
很多人会担心：所有事都经过一个前台，它会不会成瓶颈？ 他们的做法：前台推理的这一轮里到达的事件先排队，下一轮合成一批一起送进模型。前台每一步都是长输入、短输出，合在一起的事件在 Prefill 阶段并行计算，所以单次请求耗时涨得比批大小慢得多。 压测数字：需要决策的事件从每分钟约 1 条加到约 40 条，平均一批从 1.0 条涨到 2.8 条，单次请求从 2.5 秒到 3.9 秒，摊到每个决策的推理时间反而从 6.4 秒降到 1.6 秒。 （一个决策可能要好几次 LLM 请求，比如先召回上下文再派活，所以每决策时间可以大于每请求时间。） 结论：按他们现在团队的规模，不需要为了吞吐提前把前台拆成多个，拆了反而丢全局连续性。真要扩展，可以多级过滤或水平分片，但分得越细，共享的记忆越少。

Fast/Slow 的思路也用在路由上：前台只处理新任务的冷启动和跨任务协调，已有主人的后续事件由代码直接送达。 同一个 PR、同一串话题回复、同一封邮件往来，原文叫一个 Thread。前台为一个 Thread 的第一个事件派了 Worker 后，这个 Worker 就订阅这个 Thread；之后的事件由代码直接送过去，前台不用再调一次工具去转发。前台仍然能看到所有事件，用来掌握全局，但只评估还没有订阅者的新事件。 如果新事件不属于当前任务，Worker 可以退订，或交还给前台重新派。 （按 →）订阅是多对多的：几个 Worker 订阅同一个 Thread，就能同时收到同样的事件，自己发现并解决冲突，不需要点对点通信。 原型里：飞书按话题根消息归并，GitHub 按 issue/PR 号。主聊天里不带话题的新消息，前台只有在它明确指向某个工单时才归过去——原型文档原话是「话题相似不够」。

DeepSeek Super-agent 设计文与开源原型 · 示例内容为示意
事件到了目标会话之后，要往上下文里放多少？放太多，窗口被塞满，模型注意力被冲淡；放太少，模型得反复调工具去读，步骤变多。原文一句话：浪费上下文窗口，就是浪费模型的智力。 所以把有限的窗口当缓存。两个基本操作：Inline，把马上可能要用的信息直接放进窗口，省掉工具往返；Spill，超预算或很少用的完整信息放在窗口外，窗口里只留引用或摘要。 （按 → 逐步）配合「局部性」： 第一步，只给当前对象的 ID 和内容摘要； 第二步，按局部性逐步内联：先放紧密相关对象的 ID，再放时间或空间上相邻的内容，比如原文前 50 个字、这条消息前后的 IM 消息、它回复的那条、同一个代码评审讨论里相邻的评论； 第三步，超出长度的就截断，留个指针，模型需要时再调工具读后面的。 这页的话题和 PR 编号都是示意。

前台有自己的上下文难题：很多后续消息直送给了 Worker，长期运行下来历史任务越积越多，它不可能把每个任务的完整历史都留在窗口里。但用户在另一个渠道提起一个老任务时，它还得能找回来。 做法是把 Inline & Spill 一致地用在系统里所有对象上：Trigger、Thread、Worker 会话都有唯一 ID，注入一个对象时，顺带内联与它紧密相关的对象 ID。这些 ID 把对象连成一张引用图。 每次通过工具召回一个对象，返回结果也遵循 Inline & Spill，带上下一跳对象的摘要和 ID。于是模型可以从当前事件出发，按需要一跳跳召回下去。原文叫 Chain of Recall。 原文举的例子正是这条链：从当前消息的 Thread 出发，顺着内联的 ID 找到相关的 Worker 会话，再找到和那个 Worker 关联的另一个代码评审 Thread。

DeepSeek Harness 已实现这套异步机制，但默认没开
经典 ReAct 循环里，模型调一个同步的 run() 工具，循环就一直阻塞到工具结束、返回最终结果。这期间会话没法回应任何新消息。 要去掉这个阻塞，对话得从轮流说话的半双工，变成全双工。做法是把耗时的命令和工具换成异步的 start() 和 stop()：start() 立刻返回「已启动」，循环不等；工具在后台跑完后，系统把结果作为一条新事件送回会话。跑太久，模型也可以根据上下文调 stop() 结束它。 这样前台对话和后台任务解耦了：耗时任务跑着，Agent 照样回应人；新输入在当前推理步结束时就能处理，不用等后台工具。 注意：回得快，不等于你的新指令已经安全地作用到正在跑的任务上，取消、版本这些还要另外处理。

DeepSeek Super-agent 设计文与开源原型
本地 Agent 默认把三样东西绑在一台设备上：跑 Agent 循环的计算、要持久保存的会话状态、执行环境（代码仓库、本地工具链）。设备一睡眠或离线，Agent 就停；也够不着别的设备上的环境。 他们借的是存算分离，分两步解耦： 第一步，计算和状态分开：Agent 循环跑在无状态、可弹性扩缩的云容器里，会话和其它持久状态进数据库。容器可以扩、重启、替换，任务的连续性靠存储保住。 第二步，计算和执行环境分开：真实环境里有未提交的改动、私有凭证、内网依赖、特定硬件，同步到云上又贵又容易漏；让用户整个搬去云上，迁移成本又太高。所以环境留在原地，每台端只装一个轻量 daemon，不存会话状态，只负责执行命令、回结果。 这就是 BYOM：把自己的开发机或个人电脑接到云上的 Agent，也支持云上机器和按需环境。设备断断续续在线也行：重新连上后，需要在这台设备上跑的任务会自动开始、做完。 文章自己对比了 Anthropic 的《Decoupling the brain from the hands》：思路一样，区别是 Anthropic 那篇讲托管服务，DeepSeek 先要接的是每个人每天用的开发机。 （页面底部的小动画演示开发机掉线再重连。）

我们的看法与疑问，不是原文结论

身边的小例子，规模很小，没做过对照实验
这页只是举个身边的例子，规模很小，也没有做过像样的对照实验。 和 Super-agent 一对照，骨架几乎一样：一个入口、几个各管一摊的执行者、事件或定时触发、状态写在外面。 差距主要在三处：同一话题的后续消息还要经入口读一遍再转，不够程序化；没有持续运行的 Watchdog，检查一天一次；主动性弱，主要是定时做固定的活。 还没解决的：一条不带上下文的新消息到底该归哪件事。

DeepSeek Super-agent 设计文 · 第 8 节
原文第 8 节自己列了四类开放问题： 一、两层架构怎么扩展：任务变大、耦合变紧以后，前台什么时候拆、拆多细，Worker 之间什么时候直连、用什么拓扑；也可以为前台的工作专门训练模型。记忆也是扩展的上限：引用图主要解决近期任务的按需召回，跑上几个月，长期记忆会成为主要瓶颈。 二、没有会话之后怎么和 Agent 协作：界面上的对话不再对应底层会话，任务怎么展示、项目怎么管理；作者认为聊天窗口成为中心部分是路径依赖，更多交互可能会移到 GitHub 这类领域界面里。还要让人能在后台执行中随时插手、接管。 三、上下文边界和 A2A：组织变大以后，「怎么部署 Super-agent」本质上是在决定哪些上下文共享、哪些隔离。隔离的实例之间协作，就是 A2A——比如每个人的个人 Agent 和团队共享的 Super-agent。我们自己补一句：要分开想知识、执行、决策、责任四道边界，共享文档不等于共享实例，更不等于共享决定权。 四、安全和隐私：事件驱动让更多不可信输入能驱动 Agent；云端循环一旦被入侵或注入，所有连着的端设备都可能被接管；就算云端没出事，凭证只要能进模型上下文，正常执行也可能泄露。所以要「能用凭证，但看不到凭证」。
