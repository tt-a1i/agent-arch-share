一句话：一个会话太挤，五个会话太散，所以分两层。 别说错：「多个会话不好并发」是错的——多个会话本来就能并行，卡的是人要来回切。真正会被同步工具卡住的，是「一个会话里塞所有事」。 被问到「单会话加 subagent 不也行吗」：可以，但要靠 prompt 让它记得委派，后面实验会看到这不稳。 （按 → 逐个出现） 这是连续性和吞吐之间的取舍。 全塞一个会话：上下文最连贯，因为它什么都看得到；但 ReAct 一次走一步，任务一多就慢，几件事的中间过程混在一起，结果也会变差。 每件事开一个新会话：并发最高；但任务之间不完全独立时，没有全局上下文，结果对不上；几个会话分别回复你，也很乱。 所以分两层：一个常驻的前台保证连贯，后面一层隔离的会话负责并发。 原文有句话值得记：让用户自己管会话，很大程度上是从底层 LLM API 带过来的习惯。会话应该是系统的实现细节，不该是用户的心智负担。

很多人会担心：所有事都经过一个前台，它会不会成瓶颈？ 他们的做法：前台推理的这一轮里到达的事件先排队，下一轮合成一批一起送进模型。前台每一步都是长输入、短输出，合在一起的事件在 Prefill 阶段并行计算，所以单次请求耗时涨得比批大小慢得多。 压测数字：需要决策的事件从每分钟约 1 条加到约 40 条，平均一批从 1.0 条涨到 2.8 条，单次请求从 2.5 秒到 3.9 秒，摊到每个决策的推理时间反而从 6.4 秒降到 1.6 秒。 （一个决策可能要好几次 LLM 请求，比如先召回上下文再派活，所以每决策时间可以大于每请求时间。） 结论：按他们现在团队的规模，不需要为了吞吐提前把前台拆成多个，拆了反而丢全局连续性。真要扩展，可以多级过滤或水平分片，但分得越细，共享的记忆越少。

一句话：Inline 是「提前放进来」，Spill 是「先放外面、留个引用」——它们决定信息放在哪；下一页的 Chain of Recall 决定怎么把外面的找回来。 别说错：Inline 不是「从任务里直接拿到的信息」，而是系统挑出来、提前塞进上下文的信息；Spill 也不是「往回追溯」，追溯是下一页的事。 事件到了目标会话之后，要往上下文里放多少？放太多，窗口被塞满，模型注意力被冲淡；放太少，模型得反复调工具去读，步骤变多。原文一句话：浪费上下文窗口，就是浪费模型的智力。 所以把有限的窗口当缓存。两个基本操作：Inline，把马上可能要用的信息直接放进窗口，省掉工具往返；Spill，超预算或很少用的完整信息放在窗口外，窗口里只留引用或摘要。 （按 → 逐步）配合「局部性」： 第一步，只给当前对象的 ID 和内容摘要； 第二步，按局部性逐步内联：先放紧密相关对象的 ID，再放时间或空间上相邻的内容，比如原文前 50 个字、这条消息前后的 IM 消息、它回复的那条、同一个代码评审讨论里相邻的评论； 第三步，超出长度的就截断，留个指针，模型需要时再调工具读后面的。 这页的话题和 PR 编号都是示意。

一句话：靠的是系统里存好的 ID 关系，模型顺着关系一跳跳查，而不是靠 prompt 让它自己去猜去哪找。 被问到「这比项目里放几个 markdown 记忆文件好吗」：不一定，也不冲突。可以把项目知识存在文件里，顺着 ID 链找到这些文件，再把最相关的部分 Inline 进来。哪种更省、更准，要实测。 前台有自己的上下文难题：很多后续消息直送给了 Worker，长期运行下来历史任务越积越多，它不可能把每个任务的完整历史都留在窗口里。但用户在另一个渠道提起一个老任务时，它还得能找回来。 做法是把 Inline & Spill 一致地用在系统里所有对象上：Trigger、Thread、Worker 会话都有唯一 ID，注入一个对象时，顺带内联与它紧密相关的对象 ID。这些 ID 把对象连成一张引用图。 每次通过工具召回一个对象，返回结果也遵循 Inline & Spill，带上下一跳对象的摘要和 ID。于是模型可以从当前事件出发，按需要一跳跳召回下去。原文叫 Chain of Recall。 原文举的例子正是这条链：从当前消息的 Thread 出发，顺着内联的 ID 找到相关的 Worker 会话，再找到和那个 Worker 关联的另一个代码评审 Thread。

DeepSeek Harness 已实现这套异步机制，但默认没开
一句话：异步 ReAct 解决的是「一个会话内部」被慢工具卡住的问题。 别说错：异步 ReAct 不等于「把任务交给 Worker」。交给 Worker 是任务之间的并行；这里是同一个会话等工具时不卡。下一页专门对比。 经典 ReAct 循环里，模型调一个同步的 run() 工具，循环就一直阻塞到工具结束、返回最终结果。这期间会话没法回应任何新消息。 要去掉这个阻塞，对话得从轮流说话的半双工，变成全双工。做法是把耗时的命令和工具换成异步的 start() 和 stop()：start() 立刻返回「已启动」，循环不等；工具在后台跑完后，系统把结果作为一条新事件送回会话。跑太久，模型也可以根据上下文调 stop() 结束它。 这样前台对话和后台任务解耦了：耗时任务跑着，Agent 照样回应人；新输入在当前推理步结束时就能处理，不用等后台工具。 注意：回得快，不等于你的新指令已经安全地作用到正在跑的任务上，取消、版本这些还要另外处理。

本地 Agent 默认把三样东西绑在一台设备上：跑 Agent 循环的计算、要持久保存的会话状态、执行环境（代码仓库、本地工具链）。设备一睡眠或离线，Agent 就停；也够不着别的设备上的环境。 他们借的是存算分离，分两步解耦： 第一步，计算和状态分开：Agent 循环跑在无状态、可弹性扩缩的云容器里，会话和其它持久状态进数据库。容器可以扩、重启、替换，任务的连续性靠存储保住。 第二步，计算和执行环境分开：真实环境里有未提交的改动、私有凭证、内网依赖、特定硬件，同步到云上又贵又容易漏；让用户整个搬去云上，迁移成本又太高。所以环境留在原地，每台端只装一个轻量 daemon，不存会话状态，只负责执行命令、回结果。 这就是 BYOM：把自己的开发机或个人电脑接到云上的 Agent，也支持云上机器和按需环境。设备断断续续在线也行：重新连上后，需要在这台设备上跑的任务会自动开始、做完。 文章自己对比了 Anthropic 的《Decoupling the brain from the hands》：思路一样，区别是 Anthropic 那篇讲托管服务，DeepSeek 先要接的是每个人每天用的开发机。 （页面底部的小动画演示开发机掉线再重连。）
