DeepSeek 设计文 §1 · 目标能力，后续页面展开实现与限制
这一页先讲四个目标，不急着介绍实现模块。 第一，连续性。即使底层使用不同会话，用户的任务关系和相关上下文仍能延续。比如在 IM 改需求，到了 GitHub 评审仍接得上。连续的是交互和任务语义，不要求同一个 Session 永远运行。 第二，多任务执行能力。几件事可以并行推进，长任务执行期间仍能及时接新请求。原文还强调任务结果的质量；并行只是其中一部分，不应把能接收多个请求等同于真正有产出。 第三，主动性。系统持续接收环境事件，在既定授权和策略下判断是否值得行动。并非每条消息都要处理，更不意味着事件能自动授予权限。 第四，持续运行。系统保存持久状态，并在长期运行出现故障时尝试恢复。它强调的是持续服务和恢复能力，不保证永不宕机，也不保证任意中间状态都能无损恢复。本地设备离线时，依赖它的操作仍需等待。 Continuous 关心任务和交互能否接续；Persistent 关心系统能否长期运行、保留状态并恢复。下面看 DeepSeek 怎样用系统架构把这些目标组织起来。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236

DeepSeek Super-agent 设计文与开源原型
一个会话保留完整历史，但多个任务的过程会混在一起。每件事独立开会话，能并行、能隔离，但任务之间的联系和对人的回复需要额外协调。 两层架构的选择是：用一个长期存在的入口掌握任务之间的关系，让独立 Worker 执行完整任务。 这里比较的是组织方式的取舍。并非前两种方式在所有场景都不能用，简单任务未必需要两层。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236

原文 §3.3 · 并列的上下文构建规则，不对应三轮模型推理 · 右图内容为示意
这一页讲系统如何组织提供给模型的信息。左边是可以同时使用的构建规则，不是模型依次执行的三个步骤，也不代表要发起三轮模型调用。 举例：PR #42 收到一条 Safari 白屏的反馈。系统可以在准备输入时，同时给出当前对象的 ID、摘要、关联 PR 和 Worker，附带被回复的消息、邻近讨论，再为放不下的完整内容留下引用。右侧展示的是这些规则共同作用后的一份上下文示意，不是标准 API 或规定的数据结构。 Inline 是把预计马上有用的内容直接放入窗口，减少后续工具往返。Spill 是把超出预算或暂时不常用的完整内容保留在外部，在窗口里留下摘要或读取引用。 模型拿到这些输入后，信息够用就处理；信息不足再调用工具按引用读取。工具返回内容也可以遵循同样的规则，因此上下文组织既发生在事件注入时，也发生在后续工具返回时。 原文按“最小信息、利用局部性补充、超长内容外置”讲策略如何逐步完善，没有规定每条事件必须分三轮推理。原文举过前 50 个字符的例子，但不是统一的固定参数，所以图中只写消息预览。 这些原则适用于 Router 和 Worker。它权衡窗口占用、信息相关性与检索开销，不保证在所有任务里都更省。下一页再讲，Router 如何沿着对象之间的关系找回跨话题、跨会话的历史。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236

原文 §3.4 · 投机执行：事件系统之上的主动行动策略
前面讲事件怎么进入系统、怎么找到 Worker、怎么组织上下文。这一页是建立在这些机制之上的一种主动行动策略，原文把它类比为投机执行（Speculative Execution）。它不代表事件驱动架构的全部。 例如群里有人报 bug，团队事先允许 Agent 静默尝试复现和找修复。它可以先在后台做准备，确认问题并找到简单修复后，再交付有用结果；没有可交付成果时，尽量不主动打扰用户。个人场景可以先查会议冲突、收集背景和起草回复。 要区分对外通知和内部记录。原文对一般投机执行说，结果有用就交付，其余丢弃；但这不能解释为系统会删除所有失败日志或执行记录。这页只表达“不主动通知”的策略，不声称公开原型已经有某种统一的记录保留机制。实际实现应另行明确如何保留和检查必要的执行证据。 主动工作要在既定授权内。后台准备和对外提交有不同影响，不能仅因事件到达就获得执行或发布权限。没有成果时保持安静也不应被推广成所有失败、阻塞和授权问题都不报告；那些仍需遵循任务的汇报和升级规则。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236

多个 Worker：任务间并行 · 异步工具：会话内不阻塞（原文 §4.1）

DeepSeek 设计文 §5 · 架构示意，假设云端服务与存储正常可用
先看一个具体场景：修复需要 Mac 上还没提交的代码，但 Mac 离线了。此时这部分本地操作无法继续。不过，云端仍可以接消息、保存状态，也可以处理不依赖这台 Mac、且其他环境具备所需条件的任务。 为什么能这样？因为作者把三部分分开。Agent Loop 负责推进任务，Session 数据库持久保存状态，执行环境负责真正运行命令。图中横向箭头是状态读写，向下的线是远程工具调用；到 Mac 的虚线表示当前不可用。云端机器并不会凭空拥有 Mac 上的未提交改动。 BYOM 就是接入自己的机器。Mac 上的轻量 daemon 接命令、回结果，真实代码和工具链可以留在本地，不必把整个环境迁走。手机发指令、Mac 执行本身并不能证明计算也已经在云端，要看 Agent Loop 实际部署在哪里。 原文进一步把循环计算放进无状态容器，持久状态另存数据库。“无状态”说的是容器不独占持久记录，不是 Agent 没有记忆，也不等于模型推理服务就部署在这个容器里。 等 Mac 恢复连接，作者的目标是让依赖它的任务继续运行。具体怎样恢复、在途命令如何确认，需要实现支持；这一页不承诺任意一步都能无损重放，也不展开队列、幂等或检查点的具体方案。 这里讲的是设计文章，不表示公开原型已完整实现所有能力。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236

原文 §7 · 合成负载，每方案 5 次；编码用耗时工具模拟 · 缓存读取量为所有会话合计，不等于总费用
这里我们只看一个开关：后续事件有没有经过代码直送。两边都是 Router / Worker 两层架构，关闭直送后，后续消息需要 Router 再判断和转发。 结果很直观：每次运行所有会话的缓存读取量从 23.2M 增至 31.8M，约增加 37%；Router 的决策次数约增加 30%。但完成时间的中位数和 p95 基本相当。这说明在这组负载里，直送的主要收益是减少额外读取和路由开销。 为什么多花了 token，时间却没明显增加？原文第 7.2 节解释，Router 会把一轮推理期间积累的事件合并到下一轮，关闭直送后负载上升仍未达到吞吐上限。我们可以进一步推测，额外路由没有成为整体完成时间的主要瓶颈，但实验没有逐项拆分各因素的贡献。 如果有人追问批处理：作者单独压测 Router，事件到达率从每分钟约 1 条到 40 条，平均批大小从 1.0 到 2.8，单次请求耗时从 2.5 秒到 3.9 秒，每决策摊销推理时间从 6.4 秒到 1.6 秒。一个决策可能包含多次模型请求。 实验边界用一句话交代即可：这是合成消息流，每次约 300 条消息、约 20 个工作请求，每种设计跑 5 次，编码只用耗时工具模拟。它测的是调度表现，没有验证真实代码质量。缓存读取也不能直接换算为总账单，不能说“费用增加了 37%”。p95 是第 95 百分位完成时间，不是最慢 5% 的平均值。 延伸讨论可以问：在我们的任务里，哪些消息有明确归属，可以省掉一次模型判断？最终还要用真实任务看人工介入、返工和总成本。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236 主画面只保留这一个开关实验，完整消融与批处理压测在原文第 7 节，不能把局部结果扩展为所有任务上的收益。

我们的分析框架 · 示意流程，非性能曲线或定量实验结论
这里不提出“十倍 Agent 只能带来几倍收益”的数字，因为我们没有做过这种测量。先把并行执行能力与有效生产力分开：更多 Agent 能同时尝试更多工作，但下游还要处理任务依赖、上下文交接、修改冲突、结果验证以及人的决策。 按右键先看中间：任务能否拆成独立单元，往往比能启动多少进程更重要。互相依赖的任务会等待；多个修改碰到同一接口要协调；看起来完成的结果还要验收。 再看右边：有效结果是可接受、可使用的产出，不是消息量、运行时长或 PR 数。增加 Agent 也可能降低某些等待，所以不能预先断言一定出现负收益。 最后回到人的注意力：如果每个 Worker 都找你确认，系统的执行并发上去了，人的决策吞吐却没变。这与前面的统一入口、任务粒度和交接成本是同一个问题的不同层面。 建议用同类任务比较完成质量、返工次数、人工介入、等待与总成本。这是后续验证方向，不是 DeepSeek 已验证的规模化定律。

我们的讨论方向 · 实验结果来自合成负载，真实收益仍需验证
这篇文章给出了一组值得参考的系统设计：把会话管理、事件路由和持续运行更多地交给系统。模拟实验提供了调度方面的初步证据。 我们的判断是，下一步要把“省注意力”落实到真实工作里：到底少了哪些跟进和决策？出了冲突能否正确处理？增加的成本换回多少有效产出？ 如果继续试，可以先挑一个真实流程，记录人工介入和结果质量，再比较是否加入话题直送或独立巡检。一次只改变少量机制，才容易知道收益来自哪里。 组织里的上下文边界、A2A、安全和长期记忆，原文也承认尚待解决，可以在讨论环节继续展开。 资料：https://x.com/DeepSeekHarness/status/2116857257245987236 前一页进一步提出：智能能力与并发增加，不自动等于有效产出增加。我们的结论是优先验证有效生产力，在可控的协调与运行成本下，让人更容易把事情推进。
