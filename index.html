0301 · 问题与起点人的注意力上限3 / 28

模型越来越快之后，卡住的变成了人

3–5

文章作者的经验值：一个人同时能跟住的活跃会话，大概只有 3 到 5 个。

做单件事时，瓶颈是模型聪不聪明；同时推进七八件事时，瓶颈变成了你的注意力和精力。

痛点 01
同步等人

传统单会话是一问一答：它在跑慢命令时你得等它，它停下来问一句确认时所有后续步骤都得等你。

痛点 02
上下文串味

把修 bug、审 PR、查文档塞进同一个会话里，中间过程交织在一起，越聊越贵、模型注意力也越分散。

痛点 03
合上电脑就停

给本地单会话多接几个 CLI、MCP 或外部插件，并没有改变生命周期绑定本机的问题——机器休眠，活就断了。

来源：DeepSeek《Exploring Super-agent Design》第 1 节互动模拟：会话越开越多会怎样
文章开篇提出了一个大家很有共鸣的观察：过去一年单任务 coding agent 越来越强，但当我们同时开好几个窗口干活时，人要手动在窗口之间来回切、记着每个窗口做到哪了，一般跟 3–5 个就到极限了。 只给现有的本地单会话接更多 CLI 或 MCP 连接器，解决不了同步阻塞、上下文混杂和设备离线即停这三个根子上的问题。 右下角可以点开互动模拟：看看当任务超过 5 个时，「人直接盯每个会话」和「由前台替你挡掉小确认」的区别。
0401 · 问题与起点我们的第一个追问 · 拆解「注意力成本」4 / 28

但先多问一句：五个窗口合成一个入口，脑子就不累了吗？

读到这里我们冒出的第一个疑问：就算把 5 个会话收拢成 1 个聊天入口，背后的 5 个项目依然是 5 套完全不同的业务背景。

01 · 入口操作成本
找哪个窗口？
统一入口能明显改善

不用手动建会话、切标签页、记着哪个话在哪个渠道说的——系统替你路由和归档。

02 · 认知切换成本
脑子装哪套前提？
光靠合成一个窗口消不掉

上一秒看布局 PR 的接口取舍，下一秒批复排期延期邮件——人脑还是要重新加载整套上下文。

03 · 拍板决策成本
敢不敢点头？
取决于证据是否可信

如果只给你一句压缩后的结论，没有把前提条件、测试证据和风险摊开，人反而更不敢拍板。

04 · 异常接管成本
跑偏了怎么补课？
自治越久，接管可能越贵

Agent 在后台自己跑了几十步才卡住，你临时插手时，得先把这几十步做了什么、改坏了什么补回来。

结论：省掉窗口切换只是第一步；真正决定人累不累的，是每次被打断时要重新装载多少业务前提。
延伸思考：区分入口管理成本、认知切换成本、决策成本与接管成本动画对比：入口切换 vs 认知重载
这是我们读文章时讨论得最深的一个点：不能把「统一对话入口」直接等同于「消除人的认知负担」。 把 5 个窗口合成 1 个窗口，省下的是「找窗口、传话」的操作成本；但只要这 5 件事本身属于不同的项目，每当系统向你汇报或请你拍板时，你的大脑依然要做一次完整的上下文切换。 更进一步，这里还有一个「自主性悖论」：Agent 自己跑得越久，你平时越省心，可一旦它在第 40 步出了问题要你接管，你回头补课的成本反而更高。所以系统不仅要会「少打扰」，还要在打扰你时附上结构化的前提和可追溯的证据链。 点开右下角的动画页，可以直观看到「界面入口切换次数」和「大脑认知重载次数」的对比。
0501 · 问题与起点从分布式系统到多 Agent 的扩展性定律5 / 28

算力与单点智能涨十倍，协作产出会涨十倍吗？

一个值得借过来的经典问题：过去二十年算力与网络翻了几个数量级，刷短视频、搜网页的并发规模涨了万倍，为什么一局多人实时对战游戏还是几十个人、还要分服？

第一层 · 单体智能规模
1 个 Agent 能做多难的事？

主要受限于模型推理能力、工具调用可靠性与单会话上下文容量。这一层进步最快。

第二层 · 多 Agent 协作规模
10 个 Agent 有 10 倍交付吗？

一旦任务共享同一份代码库或状态，通信同步、接口冲突、锁等待与返工就会快速吃掉并行收益。

第三层 · 人机治理与价值规模
做完 100 件事 = 100 倍价值？

执行端每天交 100 个 PR，人只能审 15 个；或者方向选错了，跑得越快、制造的无用功和审查积压越多。

有效产出 ≈ 总执行产出 − 协调与等待损耗 − 冲突返工 − 验收失败与无价值工作
三个层次不能混为一谈
背景启发：由多人实时交互系统与互联网平台扩展差异的讨论延伸至多 Agent 系统（概念关系示意）
在进具体架构之前，我们可以先把视野拉高一层。 为什么短视频、搜索可以靠缓存、分片、最终一致性轻松扩到千万并发，而实时同场对战和紧耦合协作却很难同比例放大？因为后者受限于实时共享状态和强一致性。 放到 Agent 上也是一模一样的道理：单个 Agent 变聪明了，不代表开 10 个、100 个 Agent 就能拿到 10 倍、100 倍的有效交付。 有效产出等于总执行量扣掉协调损耗、冲突返工、还有人工验收卡住和做错方向的部分。带着这把尺子去看 DeepSeek 的架构，就会特别清楚它每一招到底在减哪一项损耗。
0602 · DeepSeek 怎么拆四个特征与背后的计算机系统老办法6 / 28

他们的思路：把 Agent 从“单次聊天窗口”变成一直在线的同事

Continuous · 连续
一直是同一个它

你在飞书里定方案 A，再去 GitHub PR 评论改成方案 B，它知道这是同一件事，不用你手动搬运前情。

Productive · 高产
并行且随时接活

后台可以同时推进好几个复杂任务；上一个任务还没跑完，前台随时能接你的下一句指令。

Proactive · 主动
自己留意但克制

监听群聊、PR、邮件和 CI 事件，看到真正值得处理的事才出手，其余时候保持安静不刷屏。

Persistent · 常驻
不断线、能自愈

文章很坦诚：没有提任何新理论，而是把计算机系统里的经典思想搬到了 Agent 上 单个 ReAct 循环给不了这四点
控制面 / 数据面分离 → Router + Worker Fast / Slow Path → 代码过滤 + 直送 Batching → 事件排队合并推理 Cache & Locality → Inline & Spill Speculative Execution → 后台静默先做 存算分离 → 云端循环 + 状态库 + 端上 Daemon Control Loop → 独立 Watchdog
来源：DeepSeek《Exploring Super-agent Design》第 1 节与第 9 节
DeepSeek 把理想中的 Super-agent 概括成四个词：Continuous、Productive、Proactive、Persistent。 文章里有一句话很实在：这四个特征靠单个 ReAct 循环是绝对做不到的，必须靠外围的系统架构；而且他们不觉得自己发明了什么新理论，核心做法就是把操作系统、编译器和分布式系统里成熟的工程手段——快慢路径、批处理、缓存局部性、投机执行、存算分离、看门狗——逐个搬过来解决 Agent 的问题。

0802 · DeepSeek 怎么拆两层架构（Router + Worker）与事件批处理8 / 28

拆成两层：前台只管全局连续，后台只管并发干活

前台 · Router 层（常驻）
唯一的对话入口、协调点与全局记忆

接收所有渠道的人机交互，决定开新任务还是归并旧任务，把 Worker 的结果按渠道格式转达给人。
关键约束：自己绝不执行具体任务，可以完全不给 Bash 工具；通常用轻量模型就够。

后台 · Worker 层（按任务隔离）
一个任务一个干净会话，配全套工具与强模型

每个 Worker 专注做好一件事（内部也可以再调子 agent 或组成小团队），推理过程和密集的命令调用留在自己会话里，绝不直接向外部群聊刷屏，只向 Router 汇报关键结论。

和常见 Agent Team 的核心区别

Agent Team 的 Team Lead 往往要把一个复杂任务拆成多步、频繁协调各个角色，推理负担很重；Super-agent 的 Router 只按完整任务派发、不拆解步骤。

为什么单个 Router 不容易卡死？自动批处理（Batching）

Router 推理一轮期间到达的新事件会自动排队，在下一轮合并进同一次 LLM 调用并行 Prefill。输入长、输出短，越忙单次决策摊下来的耗时反而越低。

来源：DeepSeek《Exploring Super-agent Design》第 2.1–2.2 节
为什么要拆成两层？因为「上下文连续」和「高并发吞吐」天然矛盾：所有事塞一个会话里最连续，但串行又慢又串味；每来一件事开个新会话并发最高，但彼此不知道对方在干嘛，几个窗口同时找你说话更乱。 拆成 Router + Worker 两层后，「会话（Session）」就变成了系统内部的实现细节，不再需要用户手动去管。 这里有两个很精妙的工程点： 第一，Router 只派发、不拆解任务，而且从结构上不给它 Bash 工具，防止它忍不住自己下场写代码把入口堵死； 第二，Router 天然支持批处理（Batching）——上一轮推理时积压的几个事件，下一轮合在一起送进模型做并行 Prefill，所以单个长驻 Router 比直觉上更能扛并发。

3.4 · 投机执行（Acting Ahead）
后台静默先做，有把握才出声

群里有人反馈疑似 bug，哪怕没 @ Agent，它也先在后台静默尝试复现和修复；只有确认是真问题且找到了简单修法时才把结果发出来，否则全程保持安静——用后台算力换人的零打扰。

来源：DeepSeek《Exploring Super-agent Design》第 3.1 节与第 3.4 节查看完整分层结构图
一旦把 Agent 接进真实的研发群和代码仓，95% 以上的消息都是不需要它插手的噪音。如果每条消息都调一次大模型，延迟和账单都受不了。 所以他们借了系统里的 Fast Path / Slow Path： 第一道用确定性代码规则（看事件来源、群、发送者白名单，设成「只响应明确 @ 我」「作为候选」或「直接忽略」），不花一个 token 挡掉大部分噪音； 只有候选事件才进第二道，让大模型按写在 prompt 里的策略判断值不值得动。 更妙的是「投机执行（Speculative Execution）」：在他们内部的 DeepSeek Harness 用户群里，有人提了一嘴疑似 bug，Agent 后台偷偷去复现和修，修好了才发出来，没复现出来就当没发生过——既主动，又不制造噪音。

没有 `root_id` 就自成新 Thread 进 Router 评估；只有明确指向某工单时才归并，「话题相似不够」。

来源：DeepSeek《Exploring Super-agent Design》第 3.2 节与开源原型 `src/policy.ts`、`docs/004-prompts.md`动画对比：经前台转 vs 按话题直送

怎么评估新机制？有哪些小事我们现在就可以试？

方法论 · 拒绝“安心剂”式组件
加任何一层之前，先问四件事
01 · 目标是什么？

到底是为了省 Token、降延迟、提质量，还是少占人的注意力？

02 · 综合成本在哪？

除了模型调用费，还有多少排队延迟、误报打扰和人工纠偏成本？

03 · 消融后掉多少？

把 Watchdog 或某层记忆拿掉，真实任务成功率会掉吗？证明独立贡献。

04 · 适用边界在哪？

是在独立任务下成立，还是在强耦合、真实代码仓里依然成立？

低成本、可随时回退 · 现在就能试的 5 件小事
1负责接话的入口 Agent 不给执行工具（如 Bash）从系统结构上杜绝它「顺手自己干」把对话入口堵死。
2给工单和讨论串加「话题键」，后续消息用代码查表直送同个 PR、同串话题的跟进直接进对应 Worker，前台只管新话题与跨任务协调。
3IM 回复设 100 词硬上限，转述固定「结论 / 前提 / 待拍板」三段既守住打扰预算，又防止压缩摘要时把关键前提条件漏掉。
4想让 Agent 主动干活，先从「只读复现 + 只记录不操作」试跑例如新 Issue 进来先后台静默复现、写进日志，验证靠谱再逐步放开。
5权限与白名单写进宿主代码，记住「已登录 ≠ 被允许」聊天内容与文档永远只是决策输入，对外副作用动作每次单独确认。

留给大家一起讨论的六个问题

?入口合成一个之后，人在几个项目之间切换的“脑力重装成本”，怎么才能真正降下来？
?前台 Router 用轻模型到底够不够？遇到直接提问和跨任务冲突时，怎么兼顾判断质量与低延迟？
?当多个 Worker 改同一份代码或上下游接口时，在话题广播之外，最轻量的冲突协调机制长什么样？
?当系统隐藏了底层的“聊天会话”之后，我们平时在什么界面里看全局进度、中途插手或接管任务？
?想让 Agent 帮团队跟进项目，怎么在不侵犯隐私、不搞监控的前提下补齐群聊和文档之外的状态缺口？
收束全场的核心追问
当我们能同时带十个、一百个 Agent 时，更该优先优化 Agent 之间的协作效率，还是 人对整套系统的控制成本？
前五问融合了原文第 8 节开放问题与我们的延伸讨论；第六问是贯穿全场的收束命题
这六个问题留给大家一起拍砖： 前五个分别对应认知切换、Router 轻重、多 Worker 冲突、无 Session 交互界面、以及组织状态与隐私边界； 最底下这一个，是我们聊完整个系列后最想抛给大家的总问题：当执行力越来越便宜，限制我们拿到真实有效价值的，究竟是 Agent 跑得不够快、协同不够顺，还是我们对整套系统「看得清、停得住、敢拍板」的控制成本？
