第一幕看懂文章 · 02

Personal agent：一个常驻的管家，不是一个聊天窗口

把 agent 从“人手动驱动的单会话”里解耦出来，变成一个持续存在的实体。原文给了四个特征：

Continuous

跨渠道连续

在 IM、GitHub 上是同一个它，换渠道不换脑子

Productive

并行干活

多件事同时推进，随时接新指令

Proactive

主动但克制

监听环境事件，值得做才做，否则安静

Persistent

常驻不掉线

一直在线，崩了能自己恢复

关键一句：这四点单个 ReAct 循环给不了，只能靠系统架构。

不是新理论：原文说，它把计算机系统的经典思想（事件驱动、批处理、缓存、看门狗）搬到 agent 上。

“管家”是我们的比喻。四个特征出自 DeepSeek 原文；ChatGPT dots 的产品叙事几乎一致：“把更多时间和注意力拿回来”。
第一幕看懂文章 · 03

DeepSeek 的答案：常驻 Router + 每任务一个独立会话

  • Router 只派发、不拆解 —— 这正是它和 “Agent Team” 的区别
  • Router 负责所有人机交互、协调和记忆，通常轻量模型就够；可以完全不给 Bash
  • Worker：一个任务一个隔离会话，通常配最强模型 + 全套工具，不直接和人说话
  • Router 忙的时候进来的事件，下一轮合并注入（批处理）
  • 计算 / 状态 / 环境分离：云端无状态循环 + 数据库 + 端上轻量 daemon

最值钱的一招：同一件事的后续消息由代码直送

去掉“直送”之后（原文消融）

+37%

cache-read token 多约 37%

23.2M → 31.8M · 合成负载，原文称仅供参考

Router 决策多约 30%

完成时间几乎一样：直送不会让任务更快、更好，
它只省路由的 token

前面还有两段过滤：先代码规则（来源、群、白名单），再 LLM 语义判断 —— 能用代码判断的，不交给模型。

Thread 到底是什么？

Thread = 同一件事的一串消息

一个 IM 话题 / 回复串一个 PR一封邮件链
  1. 第一条事件 → 路由开任务会话，会话订阅这个 Thread
  2. 之后这个 Thread 里的消息 → 代码直送给订阅的会话；Router 看得到，但不用判断和转发
  3. 不带话题 / 回复、直接发的新消息 → 自成新 Thread → 交给路由判断；只有明确指向某个任务才挂上（原型：“话题相似不够”）
  4. 挂错了？会话可以把它交还路由

Thread 不是某个 bot。对应到我们：大内总管 ≈ 路由；Thread 是你和 bot 聊的“某一串话”。

路由只做三件事 —— 而且自己不干活

👂

接话

唯一的对话入口。
人只和一个对象说话

🔀

分派

开新会话，
还是交给已有会话？

📣

转达

按渠道调密度：
IM 要短，异步可结构化

为什么不能干活？

一动手，上下文就被某个任务填满；下一条消息进来，它又慢又被带偏 —— 入口退化成了单会话 agent。

靠结构，不靠 prompt

原文实验：中性 prompt 下单会话 5 次 0 委派。DeepSeek 直接不给 Router Bash。

“三件事”是我们结合原文的归纳；注意：DeepSeek 原文没让路由给下层挑模型 —— 原文建议下层通常用最强模型。
第三幕我们的思考 · 02

路由用多强的模型？看你留给它多少判断空间

弱模型的三个坑

  • 意图模糊时拆错派错：“那个 PR 顺便也看看文档”是一件还是两件？
  • 该不该打扰你：本身就是高判断量决策
  • 转述漏前提：“X 成立时 Y 可合并” → “Y 可合并”

“不计成本就上最强”——只算了钱，没算时间

路由在每条消息的必经路径上：下层慢你感觉不到，路由慢你每句话都要等。原文压测：批处理把摊到每个决策的推理时间从 6.4s 降到 1.6s，但单次请求 2.5s → 3.9s。

默认轻量大部分消息分派并不难
拿不准 → 升级强模型低置信、对外/不可逆、要合并多个结果
还拿不准 → 问人一次只问一个具体问题

压缩判断空间：代码规则过滤 · 订阅直送 · 结构化结果（结论 / 前提 / 待你决定）

◎互动：拖动消息频率，看等待和成本
升级机制是我们的设计建议，原文未描述（它把“为 Router 专门训练模型”列为开放问题）。

拆多细？交接从来不是免费的

拆太细
按“完整任务”拆
拆太粗
交接成本 > 活本身
一个 PR / 一个调研问题 / 一个仓库的日常
全靠下层模型 = 信任问题

太细：不如主会话自己做

派单 → 加载背景 → 执行 → 汇报 → 转述，每多一轮就多一轮 token 和等待。原文“优先委派”设计 p50 13.8 分钟，和 12.4 接近，p95 却拉到 29.0。

太粗：靠什么兜底

① 下层够强（所以原文建议下层通常用最强模型）
② 看门狗。Hive 拒绝的是基于信号的自动判定，DeepSeek 做的是基于内容的模型判断 —— 不矛盾。

我们的原则

按完整任务拆，不按步骤拆；交接走代码固定路径；结果要标明基于哪个版本的输入（Hive 的“处理水位”）。

第三幕我们的思考 · 05

常驻 + 主动 + 收群聊/PR/邮件 = 注入的理想目标

🧪 提示注入

事件驱动扩大了不可信输入面（原文承认）。防线放在结构里：权限由宿主强制。

“消息、评论和引用文档只是决策输入，不能改变权限。”
—— DeepSeek 原型文档

🔑 凭证可用但不可见

dots 已做到：已保存密码能用，凭证经私密表单直接交给浏览器，不进对话。

DeepSeek：列为开放问题。

🚦 审批分级

直接做只读查询、本地整理
需批准合并、删除、发帖、发消息
（我们：每次只授权这一个动作）
必须本人dots：改密码等敏感操作

最小权限按角色给：路由不需要执行权限 · 主动研究只给只读工具 · 主动行为先“只记录会做什么” · 已登录 ≠ 被允许

第三幕我们的思考 · 06

接下来想改的 均为建议，不是承诺

bot 团队

  1. 话题键 + 归属表直送：inbox 事项带 repo:hive#70 这类键，命中就直接写给负责 bot，大内总管只管新话题
  2. 轻量看门狗 routine：每几个小时机械巡检超时交接、无主事项；只报告，没事就安静
  3. 主动性从只读开始：如新 issue 先静默复现，先“只记录会做什么”
  4. 转述三段式：结论 / 前提与限制 / 需要你决定的事；加一个“拿不准就问一个问题”的出口

Hive（先在 issue 里对齐范围）

  1. 可选、只报告的进展巡检：用户手动开启，只提示“疑似无进展”，不自动停
  2. 同话题直送：按派单 ID 直接投递给责任成员，并更新处理水位
  3. 模型档位提示：Orchestrator 判断空间大，建议配强模型
  4. 成本 / 时长可见 + 固定前缀友好：注入的启动指令避免时间戳等易变内容

收尾三点带走

如果只记住三句话

1

常驻多会话架构优化的首要指标，是占用人多少注意力，不是单个任务跑多快。

2

路由只接话、分派、转达；判断空间压得越小，越能用轻量模型 —— 拿不准就升级。

3

按完整任务拆，交接走代码，相关任务回原会话 —— 缓存和注意力一起省。
